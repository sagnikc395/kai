# Kai v4 — Harness Engineering Task List

v2 implements the *basics* of harness engineering: a streaming tool-use loop, a tool
abstraction with JSON schemas, a registry, and a TUI that renders calls and results.
That skeleton is sound. What follows is everything the harness still doesn't do.

This document is a **task list**, not a plan. `V3.md` groups the same territory into
phases with narrative and a suggested order of work; read that for sequencing and
rationale. Read this one when you want a discrete, self-contained piece of work with a
definition of done. Each task cites the code it changes and the V3 phase it belongs to.

Tasks are numbered 1–22 and grouped by theme. Numbering is stable — refer to tasks by
number in commits and issues.

---

## Control and safety

### 1. Permission layer between arg-parsing and tool dispatch

**Problem.** `kai/core/tool_executor.py:55` calls `tool_impl.call(parsed_args)` the
instant the model emits a tool call. `bash` runs arbitrary `bash -lc` (`kai/tools/bash.py:53`),
`write` creates parent directories anywhere on disk (`kai/tools/write.py:42`), and
`edit` writes to any absolute path. Nothing is scoped to the working directory the
system prompt advertises at `kai/core/system_prompt.py:15`.

**Do.**
- New module `kai/core/permissions.py` holding a policy object consulted by
  `execute_tool_calls` after arguments are parsed and before `call()` runs.
- `Tool` gains `is_mutating() -> bool` and `permission_key(input) -> str` so approvals
  can be remembered at a useful granularity (`bash:npm test`, `edit:/abs/path`).
- Modes: `plan` (read-only tools only), `ask` (default), `acceptEdits`, `yolo`.
- Deny returns a *tool result* explaining the denial, not an exception — the model must
  be able to adapt rather than retry blindly.
- Persist allowlists to `.kai/settings.json` (project) and `~/.kai/settings.json` (user),
  project wins.

**Done when.** A model emitting `rm -rf ~` in `ask` mode is stopped, the user sees why,
and the denial reason reaches the model as a tool result.

**Depends on.** Task 3 (the TUI cannot block for approval while the loop owns a daemon
thread). **V3:** 2.1.

---

### 2. Working-directory jail for filesystem tools

**Problem.** Separate from *who approves* a call is *what is reachable at all*. `read`,
`write`, `edit`, `glob`, and `grep` accept any absolute path with no containment.

**Do.**
- Resolve every incoming path with `os.path.realpath` (following symlinks) and reject
  anything outside the session root unless explicitly allowlisted.
- The check belongs in one shared helper in `kai/tools/base.py`, not duplicated per tool.
- Allow a configured set of escapes (`~/.kai`, an explicit `--add-dir`).

**Done when.** `read` of `/etc/passwd` and a symlink pointing out of the repo both fail
with a clear, model-readable error.

**V3:** 2.1.

---

### 3. Turn cancellation

**Problem.** `_run_assistant` runs on a daemon thread (`kai/tui/tui.py:78`) and Esc /
Ctrl+C (`kai/tui/tui.py:45-46`) quit the whole application. There is no way to stop a
bad trajectory without losing the session.

**Do.**
- Thread a `threading.Event` through `run_message_loop`, checked between stream chunks
  and before each tool call in `execute_tool_calls`.
- Rebind Esc: interrupt when busy, quit when idle. Add an explicit quit binding.
- On interrupt, append a synthetic `[Request interrupted by user]` message so the model
  understands why the transcript stops mid-thought.
- Give `bash` a kill path: `subprocess.Popen(start_new_session=True)` plus `os.killpg`,
  so interrupting a hung `npm install` actually terminates the process group. The
  current `subprocess.run` (`kai/tools/bash.py:46,53`) cannot be interrupted.

**Done when.** Esc during a long `bash` returns control to the prompt within a second,
the session survives, and the next turn has coherent context.

**V3:** 1.4.

---

### 4. Loop bounds

**Problem.** `while continue_loop:` at `kai/core/message_loop.py:81` has no iteration
cap, no wall-clock budget, and no token budget. A model ping-ponging between `grep` and
`read` runs until the API errors out.

**Do.**
- Configurable `max_turns`, `max_wall_clock_seconds`, and `max_tokens_per_request` on
  the loop, defaulting to something generous but finite.
- On exhaustion, stop cleanly and tell *both* the user and the model why, rather than
  raising.
- Detect the pathological repeat case: N identical consecutive tool calls with identical
  arguments is a loop, and saying so in a tool result usually breaks it.

**Done when.** A deliberately looping prompt terminates on its own with a clear message.

**Depends on.** Task 6 for the token half. **V3:** 1.4 / 6.5.

## Context economy

### 5. Tool output budgets enforced against the model's context

**Problem.** This is the sharpest bug in the harness. `truncate_lines`
(`kai/tools/format.py:4`) is only applied in `render_result` (`kai/tools/read.py:85`), so
the *TUI* shows 20 lines while `kai/core/tool_executor.py:63` puts `result.output` into
the message list **in full**. One `bash cat` of a large file or a `grep` across
`node_modules` silently dumps the whole thing into the conversation.

**Do.**
- Add a per-tool output cap to `Tool` in `kai/tools/base.py`, enforced centrally inside
  `execute_tool_calls` before the tool message is constructed.
- Truncate the middle, keeping head and tail — the tail of a stack trace matters more
  than its middle.
- Emit an actionable marker: `[... 4,213 lines truncated. Use read with offset=4213 ...]`.
- `grep` caps total matches and reports how many it dropped; `bash` caps combined output
  and keeps both ends.
- Keep display truncation separate. The TUI cap and the context cap are different
  numbers and should stay that way.

**Done when.** `bash cat` on a 5MB file adds a bounded number of tokens to the
conversation and the model knows how to page for the rest.

**V3:** 1.1.

---

### 6. Token accounting

**Problem.** `stream_options={"include_usage": False}` at `kai/core/message_loop.py:94`
explicitly discards the one signal every context decision depends on.

**Do.**
- Flip to `include_usage: True` and thread usage through the callbacks as a `TurnStats`.
- Add `kai/core/tokens.py` with a cheap pre-flight estimator (chars/4 is fine initially).
- Accumulate input/output tokens and cost on `Conversation`; surface remaining context
  in the status bar and behind a `/cost` command.

**Done when.** The status bar shows live context utilization and cumulative session cost.

**Blocks.** Tasks 4, 7, 8. **V3:** 1.2.

---

### 7. Conversation compaction

**Problem.** `Conversation.messages` (`kai/core/conversation.py:14`) only grows. On
overflow, `kai/core/message_loop.py:96-99` swallows the API error into `on_error` and
returns, ending the turn.

**Do.**
- `kai/core/compact.py`: keep the last N turns verbatim, replace everything older with a
  summary produced by a dedicated call on a cheaper model. The summary must preserve the
  original goal, files touched, decisions made, and open threads.
- **Never split a tool-call/tool-result pair across the boundary.** A `tool_calls`
  message with no matching `role: "tool"` is a hard API error and will poison every
  subsequent request.
- Auto-trigger near 80% of the context window; expose `/compact` for manual use.
- Render a visible marker in the transcript. Silent compaction is disorienting.

**Depends on.** Task 6. **V3:** 1.3.

---

### 8. Stale tool-result eviction

**Problem.** A `read` of a file that has since been edited three times is pure noise
occupying context. Compaction (task 7) is expensive and lossy; this is the cheap
complement.

**Do.**
- Track which tool results have been superseded — a `read` of path P invalidated by a
  later `write`/`edit` to P, an old `grep` re-run with the same pattern.
- Replace the superseded result's content with a short stub
  (`[superseded — file modified at turn 14]`) rather than deleting the message, so the
  tool_call_id pairing stays intact.
- Run before compaction is considered; it often defers compaction entirely.

**Depends on.** Task 6. **V3:** 1.3 (adjacent).

---

### 9. Dynamic system prompt with project context

**Problem.** `build_system_prompt()` (`kai/core/system_prompt.py:6`) is a static f-string
with cwd, platform, and Python version. No date, no git state, no repo structure, and no
project convention file. That file convention is most of what makes an agent feel like it
knows your codebase.

**Do.**
- Walk up from cwd collecting `KAI.md` / `AGENTS.md`, nearest-last; include
  `~/.kai/KAI.md` for user-global preferences.
- Inject the current date, git branch, dirty-file count, and recent commits.
- Inject a shallow gitignore-aware directory listing (depth 2, capped).
- Add `/init` to generate a starter `KAI.md` by analyzing the repo.
- While here: the prompt says "Always use absolute paths" but nothing enforces it —
  task 2 is what makes that instruction true rather than aspirational.

**V3:** 4.1.

## Reliability

### 10. Retry with backoff on the API call

**Problem.** Both `client.chat.completions.create` (`kai/core/message_loop.py:96`) and
the mid-stream iteration (`:119`) catch bare `Exception` and `return messages`. A 429 or
a transient 5xx permanently ends the turn. Rate limits are routine on Groq.

**Do.**
- Exponential backoff with jitter for 429 / 5xx / connection errors; respect
  `retry-after`; cap at ~5 attempts.
- Classify fatal (bad API key, context overflow surviving compaction) versus retryable,
  and surface the difference in the TUI.
- Show retry attempts in the status bar so a slow turn doesn't look like a hang.

**V3:** 1.5.

---

### 11. Mid-stream failure must not lose state

**Problem.** If the stream dies after tokens have accumulated
(`kai/core/message_loop.py:119-122`), `assistant_text` is discarded and never appended.
The user saw the text stream by; the conversation has no record of it.

**Do.**
- On a mid-stream exception, append whatever assistant text accumulated, marked as
  truncated, before returning.
- If tool calls were partially accumulated but the stream died before `finish_reason`,
  discard them explicitly — a half-built `tool_calls` message is worse than none.
- Assert the invariant on the way out: every assistant message bearing `tool_calls` has a
  matching `role: "tool"` message per id.

**V3:** 1.5.

---

### 12. Tool exception containment

**Problem.** Nothing wraps `tool_impl.call(parsed_args)` at `kai/core/tool_executor.py:55`.
A concrete live bug: `optional_number_arg` does a bare `int(value)` (`kai/tools/base.py:56`)
and `kai/tools/read.py:42` calls it *outside* the tool's try block, so a model passing
`offset: "abc"` raises straight through `execute_tool_calls` and kills the turn thread —
with no tool result emitted, leaving a dangling `tool_calls` message that breaks the next
request too.

**Do.**
- Blanket try/except around every `call()`, converting any exception into a `Result` with
  `is_error=True` carrying the traceback.
- Guarantee exactly one tool message per tool call id, unconditionally.
- Fix `optional_number_arg` to raise a typed `ValueError` with a model-readable message
  rather than letting `int()` fail opaquely.

**Done when.** A tool that raises on every call degrades the turn rather than ending it,
and the model recovers.

**V3:** 1.5.

---

### 13. Central schema validation before dispatch

**Problem.** `object_schema` declares `additionalProperties: False` (`kai/tools/base.py:73`)
but nothing validates parsed JSON against it. Each tool hand-rolls `isinstance` checks
inconsistently — compare `kai/tools/write.py:27-39` with `kai/tools/edit.py:35-54` — and
those checks duplicate what the schema already states.

**Do.**
- Validate `parsed_args` against `tool.parameters()` in `execute_tool_calls` immediately
  after `json.loads` (`kai/core/tool_executor.py:43`).
- Return validation failures as error results phrased for the model: which argument, what
  was expected, what arrived.
- Delete the now-redundant per-tool manual checks.

**Done when.** Every tool's argument handling reduces to reading already-validated values.

---

### 14. Read-before-edit staleness guard

**Problem.** `kai/tools/edit.py:62` re-reads the file at call time with no check that the
model has seen the current contents. An agent editing from a stale mental model silently
clobbers changes made by the user, another tool, or a formatter.

**Do.**
- Track per-path read timestamp and content hash in session state whenever `read`
  succeeds.
- `edit` and `write` reject paths modified since the last read, with an error telling the
  model to re-read first.
- Update the tracked state after every successful write.

**Done when.** Editing a file changed externally mid-session fails loudly instead of
overwriting.

## Capability

### 15. Parallel tool execution

**Problem.** `execute_tool_calls` iterates sequentially (`kai/core/tool_executor.py:25`).
Models routinely emit three or four independent reads or greps in one batch and pay full
latency for each.

**Do.**
- Execute independent calls on a thread pool, preserving result order for the message
  list.
- Reads parallelize freely; writes to overlapping paths must serialize. Derive the
  conflict set from `is_mutating()` and the target path (task 1).
- Keep cancellation (task 3) working across the pool.

**Depends on.** Tasks 1, 3. **V3:** 6.1 (adjacent).

---

### 16. Sub-agent delegation tool

**Problem.** A search that reads forty files to answer one question permanently costs the
main context all forty files. There is no way to spend context and throw it away.

**Do.**
- A `task` tool spawning a nested `run_message_loop` with fresh context, a restricted
  tool set, its own token budget, and a recursion depth cap.
- Return only the child's final summary to the parent.
- Route child tool calls through the same permission system — no special-casing.

**Done when.** "Find every call site of X" costs the parent context one paragraph.

**Depends on.** Tasks 1, 4, 6. **V3:** 3.3 / 6.1.

---

### 17. Bash tool overhaul

**Problem.** Four distinct deficiencies in `kai/tools/bash.py`:
- Each call spawns a fresh `bash -lc` (`:53`), so `cd` never persists and every
  invocation re-sources the login profile — slow, and it inherits user aliases.
- stdout and stderr are merged (`:60-64`); the model cannot tell them apart.
- The exit code is surfaced only when output happens to be empty (`:69-70`).
- No background execution, so dev servers and test watchers are unusable.

**Do.**
- A persistent shell session per conversation, with working directory and exported
  variables surviving across calls.
- Return stdout, stderr, and exit code as distinct labeled sections, always.
- Background mode returning a handle, plus a way to poll output and kill the process.
- Honor the output budget from task 5 on each stream independently.

**Depends on.** Tasks 3 (kill path), 5. **V3:** 1.1 / 1.4.

---

### 18. Open the tool registry

**Problem.** `_init()` hardcodes six tools and `all_tools()` hardcodes the same six by key
(`kai/tools/registry.py:16-22,34-41`) — it will `KeyError` if the two lists ever drift.
Adding a tool means editing the registry.

**Do.**
- Derive `all_tools()` from the registration order rather than a second hardcoded list.
- Entry-point-based discovery so a tool can ship as a separate package.
- An MCP client merging remote tools under a namespaced prefix into `definitions()`
  (`kai/tools/registry.py:44`), routed through the same permission system.

**V3:** 4.4.

---

### 19. `todo_write` scratchpad tool

**Problem.** For multi-step tasks the model has nowhere to externalize a plan, and
long-horizon coherence suffers for it.

**Do.**
- A tool whose only job is maintaining a checklist across the turn, rendered persistently
  in the TUI rather than inline in the transcript.
- No filesystem or network access; pure session state.

**Done when.** A five-step refactor keeps its plan visible and the model updates it as it
goes. Cheapest large win in this document.

**V3:** 3.3.

## Observability and evaluation

### 20. Session persistence

**Problem.** Everything lives in `Conversation.messages` in memory. No transcript log, no
resume, no crash recovery — and no data to debug a bad trajectory after the fact.

**Do.**
- Append-as-produced JSONL at `~/.kai/sessions/<project-hash>/<session-id>.jsonl`, one
  message per line, so a crash loses at most the current message.
- `kai --continue` resumes the most recent session; `kai --resume` shows a picker.
- Store metadata: model, cumulative cost, first user message as the title.

**Blocks.** Tasks 21, 22. **V3:** 4.3.

---

### 21. Structured telemetry

**Problem.** Nothing records per-turn latency, token counts, tool call and error rates, or
which tools the model actually reaches for. Prompt and schema changes can only be
evaluated by feel.

**Do.**
- Structured events alongside the transcript: turn start/end, per-tool latency and
  outcome, retries, permission decisions, compaction firings, context utilization at each
  turn.
- Keep it machine-readable — this is the input to task 22, not a debug log.

**Depends on.** Tasks 6, 20.

---

### 22. Agent-level evaluation harness

**Problem.** `tests/test_tools.py` tests tools in isolation. Nothing exercises the loop, so
there is no way to tell whether any change above helped.

**Do.**
- A `FakeProvider` yielding scripted stream events, making the whole loop unit-testable —
  including tool errors, cancellation, retry paths, and compaction boundaries. This is the
  highest-leverage item here and it unblocks confident work on tasks 3, 7, 10, 11, 12.
- Compaction invariant test: never orphan a tool-call/tool-result pair.
- Permission matrix tests, one per mode.
- A dozen fixture repos with task prompts and assertions on final filesystem state, run
  against a real provider behind an opt-in marker.

**Depends on.** Task 20. **V3:** 5.2 (and 7.x for the external benchmark).

## Cross-cutting note: untrusted tool output

Not a numbered task because it isn't a single change. Tool output enters the conversation
as trusted text (`kai/core/tool_executor.py:58-64`), so a README, a build log, or a fetched
page can issue instructions the model will follow. Combined with the absence of task 1,
that is an unbounded write primitive.

There is no complete fix, but the mitigations live inside tasks already listed:

- **Task 1** turns injection from dangerous into merely annoying. It is the reason to
  build the permission layer before adding any tool that fetches remote content.
- **Task 2** bounds the blast radius of anything that does slip through.
- Mark tool results as untrusted content in the prompt (task 9) so the model treats
  instructions found inside them as data.
- Never auto-approve based on a `permission_key` derived from attacker-controlled text.

## Where to start

If you do nothing else: **6 → 5 → 4**. Token accounting, output budgets, and a loop cap
together are a few hundred lines, touch only `message_loop.py` and `tool_executor.py`, and
eliminate the two failure modes you will hit in daily use.

Then **12 → 10 → 3**, which are small and remove the crashes.

Then **22**, before the harness gets big enough that changing it becomes guesswork.
