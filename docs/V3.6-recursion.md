# Getting to Phase 6 — an implementation on-ramp

Companion to [`V3.md`](./V3.md) §6 and issue **#3 (V3.6: Recursive sub-agents and
sandboxed execution)**.

`V3.md` §6 says *what* to build and *why*. `V4.md` breaks the harness into discrete
tasks. Neither answers the question you actually hit when you sit down to start:
**Phase 6 is not startable today, and the interesting part of the work is everything
that has to be true before it is.** This document is that path — what blocks it, in
what order to unblock it, and which design questions have to be settled in prose
before any of it becomes code.

Read this once, then work from the stage table. Nothing here supersedes `V3.md`; it
sequences it.

## 2. Structural blockers in the current code

Three properties of the present 1,640 lines make 6.1 impossible *as specified*. All
three are worth fixing on their own merits, independent of whether recursion ever
ships. That is the argument for doing them first: none of this work is speculative.

### 2.1 The loop is synchronous top to bottom

`launch_subagent` is `async` so the parent can `asyncio.gather` independent
sub-tasks. That concurrency is the entire wall-clock claim (180.0s → 73.3s). Kai has
no async seam anywhere:

- `kai/core/message_loop.py:61` — a plain `while` loop.
- `kai/api/base.py:32` — `Backend.stream()` returns `Iterator[StreamEvent]`.
- `kai/core/tool_executor.py:25` — a `for` loop over tool calls, strictly serial.
- `kai/core/message_loop.py:87` — `time.sleep` in the retry path, which would block
  the event loop.

Converting `Backend.stream` to an `AsyncIterator` and `execute_tool_calls` to
`asyncio.gather` **is** #18. Doing #18 buys ~80% of the async conversion needed by
6.1, against a far smaller blast radius and with an immediately observable win (two
independent `grep`s stop running back to back). Do not do this conversion for the
first time inside a recursion PR.

### 2.2 Tool results are typed as strings

`kai/tools/base.py:9-11`:

```python
@dataclass
class Result:
    output: str
    is_error: bool = False
```

Design decision #2 of 6.1 — *the child returns a Python object, not a string* — is
blocked at the type level. The same constraint blocks handles: `kai/core/tool_executor.py:62`
places `result.output` directly into message content, which is the exact inversion
6.3 describes. Widening `Result` to carry a structured payload alongside its rendered
form is a prerequisite for both 6.1 and 6.3, and is independently useful to #8
(budgets need to truncate the *rendered* form while keeping the full value addressable).

### 2.3 There is no seam where permission can be enforced

`kai/core/tool_executor.py:55` calls `tool_impl.call(parsed_args)` the moment the
model emits a call. Under recursion, a depth-3 child would shell out unattended, in a
context the user never saw, possibly concurrently with three siblings. #4 is not a
nice-to-have here; it is the thing that makes concurrent children survivable. It must
also be designed to work when the approving user is *not* on the other end of the
call stack — a child's request has to propagate to the root, which is easier to build
before the tree exists than after.

## 3. The critical path

Stages are ordered. Each has a completion criterion that does not reference the next
stage — if you stop after any of them, Kai is better than it was.

### Stage A — Make the budget real
**#8 (output budgets) + #9 (token accounting).**
`max_steps` and `token_budget` in 6.5 are unenforceable without #9; there is nothing
to debit. #8 protects the JSON path forever, exactly as `V3.md:409` argues, and its
truncation markers are the model-facing contract handles will later replace.
**Done when.** A 2MB `read` cannot blow the window, and the running turn reports
tokens consumed against a ceiling.

### Stage B — Make execution governable
**#4 (permission layer).**
Design the policy object to be consulted with an *agent identity* (node id, depth),
not just a tool name and args — the recursion-aware version is nearly free now and
expensive to retrofit. Denials return a tool result, never an exception.
**Done when.** `rm -rf ~` in `ask` mode is stopped, the reason reaches the model, and
the policy call site takes a caller identity it currently ignores.

### Stage C — The gate: get a number
**5.1 (headless mode) + #2 (Terminal-Bench adapter).**
This is non-negotiable and it is where most people skip ahead. Run Harbor's five-task
oracle smoke test before writing the adapter, so you are debugging your adapter and
not your install. Record the baseline with the model, config, and commit pinned.
**Done when.** `kai --headless` solves a Terminal-Bench task end to end and you have a
committed baseline score you would be willing to defend.

> **Stop here and reassess.** Everything after this point is justified only by
> movement against that number.

### Stage D — Grow the async seam
**#18 (parallel tool execution).**
`Backend.stream` → `AsyncIterator`; `execute_tool_calls` → `asyncio.gather`;
`time.sleep` → `asyncio.sleep`. The TUI (`kai/tui/tui.py`) already runs on Textual's
event loop, so it is the natural place for the loop to live.
**Done when.** Two independent read-only tool calls in one assistant turn execute
concurrently, and the baseline from Stage C is unchanged.

### Stage E — Prove delegation works at all
**#19 (synchronous sub-agent tool).**
One level deep, JSON mode, string return, no sandbox. This is deliberately the weak
version: it isolates the question *"can this model write a good sub-task goal and use
the result?"* from concurrency, sandboxing, and handles, all of which make failures
much harder to read. Prompt it with the delegation policy from 6.5 — breadth not
depth, specify the return shape, never delegate what you already hold.
**Done when.** Depth-1 delegation runs against the Stage C baseline, and you can point
at the tree log and say why it did or did not help.

### Stage F — Context economy
**6.2 (code mode) + 6.3 (handles).**
Both stand alone as large context reductions; neither requires recursion. Build the
persistent REPL out-of-process from the start if you intend Stage G — a kernel per
agent maps onto a sandbox per agent, an in-process `InteractiveShell` does not.
**Done when.** "Read these 40 files and report the ones importing X" is one program
and one result, and a 41,208-line build log costs the context one descriptor line.

### Stage G — Isolation
**6.4, `DockerSandbox` only.**
`LocalSandbox` stays the default. You need isolation before concurrent writing
children, not before concurrent reading ones — which is another reason read-mostly
children are the right default.
**Done when.** A node executes in a container, `fork()`/`diff()` round-trips a patch,
and a conflicting patch surfaces to the model as a tool error.

### Stage H — The thing the issue is actually about
**6.1 (async `launch_subagent`) + 6.5 (budgets).**
By now async exists, delegation is prompted, handles cross boundaries, sandboxes
isolate, and there is a baseline to measure against. This stage is comparatively small.
**Done when.** Recursion off vs. on, same model, same budget, against the Stage C
baseline. Report the number whichever way it comes out.

## 4. Design questions to settle in prose before writing code

These are unresolved in `V3.md` §6 and in issue #3. Each one changes the shape of the
implementation, so settle them in writing — a paragraph each, appended to this doc.

**4.1 What actually crosses the parent/child boundary?**
6.3 says "handles, not text." But a handle is an entry in a REPL namespace, and a
child in its own sandbox has its own namespace. Either handles are serialised on
transfer — in which case you are copying, and the compression claim needs restating —
or the namespace is shared out-of-process and the sandbox boundary is not a memory
boundary. This single question determines the REPL architecture in Stage F and the
sandbox design in Stage G. Decide it before Stage F.

**4.2 Which model is the baseline?**
`kai/config.py:9` defaults to `qwen2.5-coder:7b`. That is squarely in the class RAO
showed delegates badly without training — the Oolong failure where the agent printed
the whole input into the root context and exhausted its window. A recursion-off vs.
recursion-on number measured on a 7B local model measures the model's weakness, not
the architecture. Either run Stage C's baseline on a hosted frontier model, or state
plainly in the results that the number is a lower bound. Decide it before Stage C.

**4.3 What is the unit of the write lease?**
6.4 says one write lease per path, enforced by the parent at spawn. Paths are not
known at spawn time for most useful sub-tasks. Options: declare a subtree prefix in
the goal, make writing children strictly serial, or let children write freely and
resolve at patch-apply. The third is simplest and probably right — `git apply --3way`
turns a conflict into a non-zero exit you surface as a tool error — but it means the
lease language in the issue is aspirational. Decide it before Stage G.

**4.4 What does a child return when it fails?**
Unrestricted return type means there is no natural error channel. A child that runs
out of steps, gets denied a permission, or exhausts its token budget must return
something the parent can branch on without re-parsing prose. Decide it before Stage E,
since the synchronous version has the same problem in miniature.

## 5. Instrumentation, from the first delegating commit

`V3.md:489` says log every tree from day one. Concretely, one structured record per
node, written from Stage E onward — before there is anything recursive to log:

- node id, parent id, depth, sibling index
- the goal string verbatim, and the requested return shape
- tokens in / out, wall-clock, environment steps consumed
- terminal status, and for failures which budget was hit
- for writing nodes: patch size, and whether it applied cleanly

This is not observability garnish. It is the evaluation dataset — the only way to
answer "delegate for breadth, not depth" empirically rather than by assertion, and
the only artefact that survives if the training half of RAO ever becomes in scope.
It shares everything with #21 (structured telemetry) and #22 (agent-level evaluation
harness); build it as those, not as a Phase 6 special case.

### The paper `V3.md` does not cite, and should
**Recursive Agent Harnesses** — Lumer, Sen, Paul, Subbiah. arXiv:2606.13643.
<https://arxiv.org/abs/2606.13643>

This is RAO's architecture **without** the RL training, on frontier models — exactly
the question §6.0 hedges on when it says "treat the numbers as directional." Parent
agents spawn children with tools, code execution, and planning; children run in
parallel; the design is code-first. On Oolong-Synthetic (199 samples, contexts to 4M
tokens) it reports 71.75% → 81.36% with the backbone **held fixed at GPT-5** to match
published baselines, and 89.77% with Claude Sonnet 4.5. Because the backbone is
fixed, the gain is attributable to the harness rather than the model.

It is closer to what Kai is building than RAO itself is, and it is better evidence for
#3's **Done when** than the TextCraft-Synth table. Read it before Stage E — it may
change the budget defaults in 6.5.

## 7. What "started" looks like

Not a `kai/sandbox/` directory. The first commit on this path touches
`kai/core/tool_executor.py` and adds a token counter. If the next week produces #8,
#9, #4, headless mode, and a committed Terminal-Bench baseline, Phase 6 has genuinely
begun — because every claim it makes becomes falsifiable at that moment, and not
before.
