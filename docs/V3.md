# Kai v3 — Implementation Plan

Target: take Kai from "toy agent loop that works for one question" to a CLI coding
agent that survives a real multi-hour task on a real repo.

v2 is ~1400 LOC: a Groq-only streaming tool loop (`kai/core/message_loop.py`), six
tools, and a Textual TUI. It is a good skeleton. What it lacks is everything that
keeps an agent alive over a long session: bounded context, cancellation, retries,
permissioning, persistence, and extensibility.

This document is ordered by dependency, not by excitement. Phase 1 is load-bearing
for everything after it.

---

## Current state — the concrete failure modes

Read these first; each phase below fixes one.

| # | Failure | Where |
|---|---------|-------|
| 1 | `Conversation.messages` grows unbounded. A single `grep` over a large repo can exceed the window, and every later turn 400s. | `kai/core/conversation.py:14` |
| 2 | Tool output is never truncated *for the model*. `truncate_lines` in `kai/tools/format.py` only shortens the TUI render; `result.output` goes into the message list in full. | `kai/core/tool_executor.py:56` |
| 3 | `bash -lc <anything>` runs with no gate. Same for `write` / `edit`. | `kai/tools/bash.py:43` |
| 4 | No cancellation. `_run_assistant` is a daemon thread; Esc quits the whole app. | `kai/tui/tui.py:75` |
| 5 | Any API exception silently ends the turn — rate limits are fatal instead of retried. | `kai/core/message_loop.py:97` |
| 6 | An exception inside `tool.call()` escapes `execute_tool_calls` and kills the turn instead of being fed back to the model. | `kai/core/tool_executor.py:52` |
| 7 | Provider is hardcoded Groq in five lines. | `kai/api/client.py` |
| 8 | Nothing persists. No resume, no history, no cost accounting. | — |
| 9 | System prompt is static; no project context, no `KAI.md`, no git state. | `kai/core/system_prompt.py:6` |

## Phase 1 — Survival

The agent must not fall over on the second real task. Nothing else matters until
this lands.

### 1.1 Tool output budgets

Every tool gets a hard output cap enforced *before* the result enters the message
list.

- Add `max_output_tokens` (default ~8k chars for most tools, higher for `read`)
  to `Tool` in `kai/tools/base.py`.
- Truncate in the middle, not the end — the tail of a stack trace matters more
  than the middle of it. Emit an explicit marker the model can act on:
  `[... 4,213 lines truncated. Use read with offset=N to see more ...]`
- `grep` should cap total matches and tell the model how many it dropped.
- `bash` should cap combined stdout+stderr and keep both head and tail.

Do this inside `execute_tool_calls` so it applies uniformly, with a per-tool
override. Keep the existing display truncation separate — the TUI cap and the
context cap are different numbers.

### 1.2 Token accounting

- Switch `stream_options` to `{"include_usage": True}` (`kai/core/message_loop.py:89`)
  and thread usage into a new `TurnStats` on the callbacks.
- Add `kai/core/tokens.py` with a cheap estimator (chars/4 is fine to start; swap
  in `tiktoken` or the provider's counting endpoint later) for pre-flight sizing.
- Track cumulative input/output tokens and cost on `Conversation`; surface in the
  status bar and a `/cost` command.

### 1.3 Compaction

- `kai/core/compact.py`: given a message list, keep the last N turns verbatim and
  replace everything older with a single summary message produced by a dedicated
  model call. The summary prompt should preserve: the user's original goal, files
  touched, decisions made, and anything still outstanding.
- Never split a tool-call/tool-result pair across the boundary — a dangling
  `tool_calls` message with no matching `role: "tool"` is a hard API error.
- Auto-trigger at ~80% of the model's context window; also expose `/compact`.
- Show a visible marker in the transcript when it fires. Silent compaction is
  confusing.

### 1.4 Cancellation

- Add a `threading.Event` to `run_message_loop`, checked between stream chunks and
  before each tool call in `execute_tool_calls`.
- Rebind Esc: interrupt if busy, quit if idle. Add a second binding (`ctrl+d`) for
  explicit quit.
- On interrupt, append a synthetic user message — `[Request interrupted by user]` —
  so the model understands why the transcript stops mid-thought.
- `bash` needs its own kill path: run via `subprocess.Popen` with `start_new_session=True`
  and `os.killpg` on cancel, so interrupting a hung `npm install` actually works.

### 1.5 Retries and tool error containment

- Wrap `client.chat.completions.create` in exponential backoff with jitter for
  429 / 5xx / connection errors. Respect `retry-after`. Cap at ~5 attempts.
- Wrap `tool_impl.call(parsed_args)` in try/except and return the traceback as a
  tool result with `is_error=True`. The model can usually recover from a tool
  failure; it cannot recover from the turn vanishing.
- Distinguish fatal (bad API key, context overflow after compaction) from
  retryable, and surface the difference in the TUI.

**Phase 1 exit criteria:** run Kai against a 50k-file repo, ask it to find and fix
a bug, interrupt it mid-`bash`, resume, and let it run 40+ turns without a crash or
a context error.

## Phase 2 — Trust

Now make it safe to leave running.

### 2.1 Permission system

New module `kai/core/permissions.py`.

- `Tool` gains `is_mutating() -> bool` and `permission_key(input) -> str`
  (e.g. `bash:npm test`, `edit:/abs/path`) so approvals can be remembered at a
  useful granularity.
- Modes: `plan` (read-only tools only), `ask` (default), `acceptEdits`
  (auto-approve write/edit, still ask for bash), `yolo`.
- `execute_tool_calls` consults the policy and, on a miss, raises a request through
  a new `on_permission_request` callback. The TUI blocks on a modal: allow once /
  allow always for this key / deny with feedback.
- "Deny with feedback" is important — the denial reason goes back as the tool
  result so the model adapts instead of retrying blindly.
- Persist allowlists in `.kai/settings.json` (project) and `~/.kai/settings.json`
  (user), merged project-wins.
- Ship a small deny-by-default set of dangerous patterns (`rm -rf /`, `curl | sh`,
  writes outside cwd) that require explicit confirmation even in `acceptEdits`.

### 2.2 Plan mode

Read-only mode where `bash` is restricted to a safe subset and `write`/`edit` are
unavailable. The model researches and proposes; the user approves; then it
executes. This is the single best guard against a confident agent doing damage,
and it's mostly free once 2.1 exists.

### 2.3 Checkpointing and rewind

- Before the first mutating tool call of each turn, snapshot the working tree into
  a shadow git repo at `~/.kai/checkpoints/<project-hash>` (`git --git-dir` pointed
  elsewhere so the user's own repo and index are untouched).
- `/rewind` restores files **and** truncates the message list to the matching turn.
  Restoring one without the other produces an agent that is confidently wrong about
  the state of the disk.
- Keep the last ~20 checkpoints, prune by age.

## Phase 3 — Capability

### 3.1 Provider abstraction

`kai/api/` becomes a package with a `Provider` protocol:

```python
class Provider(Protocol):
    def stream(
        self, messages: list[Message], tools: list[ToolDef], **opts
    ) -> Iterator[StreamEvent]: ...
    def context_window(self, model: str) -> int: ...
    def count_tokens(self, messages: list[Message]) -> int: ...
```

`StreamEvent` is a normalized union: `TextDelta | ToolCallDelta | Usage | Done`.
Move the accumulator logic in `kai/core/message_loop.py:29-64` behind it — that
code is OpenAI-wire-format-specific and shouldn't live in the loop.

Implementations: Anthropic, OpenAI-compatible (covers Moonshot/Kimi, DeepSeek,
OpenRouter, Ollama, vLLM in one adapter), and the existing Groq path.

Config in `.kai/config.toml`:

```toml
[provider]
default = "anthropic"

[models]
main  = "claude-sonnet-5"
small = "claude-haiku-4-5-20251001"   # compaction, titles, cheap subagents
```

Note the two-model split — compaction and subagent summarization should not run on
the expensive model.

### 3.2 Prompt caching

Once on Anthropic or Kimi, mark the system prompt + tool definitions as cacheable.
`request_messages` is already rebuilt with a stable prefix every iteration
(`kai/core/message_loop.py:79`), so this is a small change for a large cost
reduction on long loops. Also add a cache breakpoint after the compaction summary.

### 3.3 New tools

In value order:

- **`todo_write`** — a plan list the model maintains across the turn, rendered
  persistently in the TUI. Cheapest large win available; multi-step coherence
  improves sharply when the model has somewhere to externalize its plan.
- **`task`** (subagent) — spawn a nested `run_message_loop` with its own fresh
  context and a restricted tool set, return only the final summary. This is how
  you search a big repo without poisoning the main context. Needs a recursion
  depth cap and its own token budget.
- **`multi_edit`** — batched, atomic edits to one file. All-or-nothing.
- **`web_fetch`** — URL → markdown, with a size cap and an SSRF guard for private
  address ranges.
- **`web_search`** — pick one provider behind an interface.
- **`apply_patch`** — unified-diff application. More token-efficient than
  string-replace for large multi-hunk changes, and less prone to the
  "old_string not unique" failure loop.

### 3.4 Diff rendering

`EditTool.render_result` returns flat text today. Render a real colored unified
diff in the transcript. This is the difference between reviewable edits and
rubber-stamped ones.

## Phase 4 — Extensibility

### 4.1 Project memory

`build_system_prompt()` (`kai/core/system_prompt.py:6`) becomes dynamic:

- Walk up from cwd collecting `KAI.md` / `AGENTS.md`, nearest-last.
- Include `~/.kai/KAI.md` for user-global preferences.
- Inject git branch, dirty-file count, and recent commits.
- Inject a shallow directory listing (depth 2, gitignore-aware, capped).
- `/init` generates a starter `KAI.md` by analyzing the repo.

### 4.2 Slash commands

Dispatcher in `kai/core/commands.py`, intercepting input before it reaches the
model. Built-ins: `/help`, `/clear`, `/compact`, `/cost`, `/model`, `/resume`,
`/rewind`, `/init`, `/permissions`, `/plan`.

User-defined commands as markdown files in `.kai/commands/<name>.md`, with
`$ARGUMENTS` substitution and frontmatter for allowed tools. Trivial to implement,
and it's what makes the tool feel like *yours*.

### 4.3 Session persistence

- JSONL transcripts at `~/.kai/sessions/<project-hash>/<session-id>.jsonl`, one
  message per line, appended as they're produced (crash-safe).
- `kai --continue` resumes the most recent session; `kai --resume` shows a picker.
- Store metadata: model, cost, first user message as the title.

### 4.4 MCP client

stdio + streamable-HTTP transports. Servers declared in `.kai/config.toml`, their
tools namespaced (`mcp__<server>__<tool>`) and merged into `definitions()`
(`kai/tools/registry.py:44`). MCP tools route through the same permission system as
native ones — do not special-case them.

This is the ecosystem play: extensibility without you writing every integration.

### 4.5 Hooks

Shell commands fired on `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`.
`PreToolUse` can block by exit code, with stderr fed back to the model as the
denial reason. Enables auto-format on edit, protected-path enforcement, and
test-on-change without touching Kai's source.

## Phase 5 — Reach

### 5.1 Headless mode

`kai -p "fix the failing test" --output-format json`. Streams NDJSON events for
piping. Turns Kai into something scriptable in CI — and, more usefully, makes it
end-to-end testable without driving the TUI.

### 5.2 Test strategy

`tests/test_tools.py` is the only test today. Add:

- A `FakeProvider` yielding scripted `StreamEvent`s → lets you unit-test the whole
  loop, including tool errors, cancellation, and compaction boundaries.
- Compaction invariant tests: never orphan a tool-call/tool-result pair.
- Permission matrix tests per mode.
- Golden-file tests for tool rendering.
- One slow end-to-end test against a real provider, marked and opt-in.

### 5.3 TUI polish

- Persistent todo panel
- Token/cost/context-remaining in the status bar
- Streaming markdown rendering (currently raw text accumulation in
  `kai/tui/tui.py:98`)
- Collapsible tool-result blocks
- `@`-completion for file paths, `/`-completion for commands

## Phase 6 — Recursive agents and sandboxed execution

This phase is the ambitious one. It adopts the inference-time architecture from
**Recursive Agent Optimization** (Gandhi, Chakraborty, Wang, Kumar, Neubig; CMU &
Amazon AGI Labs, arXiv:2605.06639) and pairs it with per-agent VM isolation.

### 6.0 What the paper actually claims, and what carries over

RAO is an *RL training* method: it trains a single shared policy to act at every
node of a dynamically-generated recursive execution tree, teaching the model **when**
to delegate, **how** to phrase sub-tasks, and **how** to recombine child outputs.

Two parts, and only one of them is free:

- **The inference-time architecture** — recursive self-delegation with fresh child
  contexts, a code-mode action space, and handle-based context passing. This is a
  scaffold. You can build all of it in Kai with no training whatsoever.
- **The training method** — the local node reward, the leave-one-out baseline, the
  depth-weighted objective. This requires RL infrastructure and an open-weights
  model. Out of scope for a CLI tool unless you deliberately take on a research
  project (see 6.5).

Be clear-eyed about this: the paper's own framing is that prior work "treats recursion
purely as an inference-time scaffold wrapped around a pretrained model," and that
untrained models delegate badly. Their own Oolong runs show a transient failure mode
where the agent printed the entire input into the root context and exhausted its
window before relearning to chunk. So the scaffold alone gets you *some* of the
benefit — frontier models are much better at delegation than the 4B/30B models in
the paper — but don't expect the headline numbers (0.24 → 0.95 success on
TextCraft-Synth) from architecture alone. Build the scaffold because it's the right
architecture for a coding agent; treat the numbers as directional.

The results that matter most for Kai's context problem:

| Setting | Single-agent | Recursive |
|---|---|---|
| TextCraft-Synth, 8K context, hard tasks | 0.00 SR | 0.88 SR |
| TextCraft-Synth, 8K context, overall | 0.24 SR | 0.95 SR |
| TextCraft-Synth, 40K train / 256K eval, hard | 0.20 SR, 180.0s | 0.88 SR, 73.3s |
| Oolong-Real (≥55K-token inputs, 32K training limit) | — | higher avg reward at every context bucket |

An 8K-context recursive agent matched a 40K-context single agent. That is the
argument for Phase 6 in one line: **recursion is a context-compression mechanism,
and it's a better one than summarization** — because compaction (Phase 1.3) is lossy
after the fact, whereas delegation is lossy *by construction, at the boundary you
chose*.

### 6.1 The delegation primitive

RAO's action is:

```
async launch_subagent(goal, ...) -> Any
```

Four design decisions worth copying verbatim:

1. **Async.** The parent can `asyncio.gather(...)` independent sub-tasks and run
   them concurrently. This is where the wall-clock win comes from — 180s → 73s on
   hard tasks. Kai's loop is synchronous top to bottom today; this is the single
   biggest structural change in the phase.
2. **Unrestricted return type.** The child returns a Python object, not a string.
   The parent asks for whatever shape is useful downstream — a list of file paths,
   a dict of symbol → location, a patch. Strings force the parent to re-parse
   natural language, which is both lossy and token-expensive.
3. **Fresh child context.** The child gets the goal and the context it was
   explicitly handed. It does *not* inherit the parent's history. This is the
   entire point.
4. **Same policy at every node.** Not a hand-designed orchestrator/worker split.
   Any agent can delegate; trees are generated dynamically with arbitrary branching.

### 6.2 Code mode — the prerequisite

RAO's agents interleave reasoning with **code execution in a Python REPL**, not
JSON tool calls. `launch_subagent` is a function the model calls *inside* generated
code, which is why `asyncio.gather` and structured returns work at all.

For Kai this means a new execution mode alongside the current tool loop:

- Add a `python` tool backed by a **persistent** REPL — variables survive across
  turns within a session.
- Expose Kai's existing tools as Python functions inside that REPL
  (`read()`, `grep()`, `edit()`, `launch_subagent()`).
- The model writes short programs instead of emitting one tool call per turn.

Two independent wins, before recursion even enters the picture:

- **Loops collapse.** "Read these 40 files and find the ones importing X" is one
  program with one result, not 40 round-trips each dumping a full file into context.
- **Intermediate results stay out of context.** A 200KB file read into a Python
  variable and then filtered costs the context only the filtered output.

Keep the JSON tool loop as the default; code mode is opt-in per session
(`--mode code`) until it proves itself. They share the same permission system.

### 6.3 Handle-based context passing

The paper's Oolong setup is the trick to steal, and it's what directly answers
"reduce the context size":

> They pre-populate the agent's Python interpreter with a `context` string variable
> that the agent interacts with **programmatically**, rather than injecting the
> document into the prompt. The agent then passes chunks to children via
> `launch_subagent(goal: str, context: str)`.

Generalize this into a **handle** abstraction in `kai/core/handles.py`:

- Large tool results (a big file read, a wide grep, a verbose build log) are stored
  in the REPL namespace and the model sees only a descriptor:
  `<handle h3: build.log, 41,208 lines, 2.1MB>`.
- The model slices, filters, or greps the handle in code, or hands it wholesale to
  a sub-agent that reads it in a fresh context.
- Handles are what cross the parent/child boundary — not text.

This inverts the current design, where `execute_tool_calls` (`kai/core/tool_executor.py:56`)
pastes every byte of output into the message list. Phase 1.1's truncation is the
band-aid; handles are the actual fix. **Build 1.1 anyway** — it's cheap and it
protects the JSON-mode path forever — but this is where it lands.

### 6.4 Per-agent VMs

Every node in the execution tree gets its own isolated machine. Motivation is
threefold: safety (untrusted generated code), parallelism (concurrent children
must not fight over the same working tree), and reproducibility (Terminal-Bench in
Phase 7 evaluates inside containers anyway).

`kai/sandbox/` with a `Sandbox` protocol:

```python
class Sandbox(Protocol):
    def exec(self, cmd: str, timeout: float) -> ExecResult: ...
    def read(self, path: str) -> bytes: ...
    def write(self, path: str, data: bytes) -> None: ...
    def snapshot(self) -> SnapshotId: ...
    def fork(self) -> "Sandbox": ...      # child inherits parent's filesystem
    def diff(self) -> UnifiedDiff: ...    # what changed vs. the fork point
    def destroy(self) -> None: ...
```

Backends, in build order:

1. **`LocalSandbox`** — the current behavior. No isolation, cwd is the repo. Keep it
   as the default; most users do not want a container to edit their own files.
2. **`DockerSandbox`** — container per agent node. `fork()` is a commit + run,
   `diff()` is a `git diff` inside the container. Good enough for 95% of cases and
   it's what Terminal-Bench uses.
3. **`MicroVMSandbox`** — Firecracker, or a hosted equivalent (Vercel Sandbox, E2B,
   Daytona). True kernel isolation, sub-second boot, snapshot/restore. Worth it only
   if you're running genuinely untrusted code or want fast fork-per-branch.

The merge problem is the hard part, and it's the one to think about before writing
code: N children each edit a forked filesystem, and the parent must reconcile. Rules
that work:

- Children are **read-mostly by default**. Search, analysis, and investigation
  sub-agents get a read-only fork. Most delegation in a coding agent is
  investigation, and read-only children never conflict.
- A child that writes returns a **patch**, not a filesystem. The parent applies
  patches sequentially and surfaces conflicts to the model as a tool error.
- Only one child may hold a write lease on a given path at a time; the parent
  enforces this at spawn.

This also subsumes Phase 2.3 — `snapshot()` / `fork()` is a strictly better
checkpoint mechanism than the shadow git repo, and `/rewind` becomes a restore.
If you're confident you'll do Phase 6, build 2.3 directly on `LocalSandbox` and skip
the shadow-repo design.

### 6.5 Budgets, and what replaces training

RAO imposes explicit limits on **recursion depth** and on **environment steps per
agent instance**. Copy both — an untrained model with an unbounded delegation
primitive will fork-bomb your machine and your API bill.

`.kai/config.toml`:

```toml
[recursion]
max_depth        = 4      # paper: trained at 6, eval to 12; DeepDive used 4
max_children     = 8      # per node
max_steps        = 40     # env steps per agent instance
max_concurrent   = 4      # global cap on live sandboxes
token_budget     = 200000 # per subtree, parent's budget is debited by children
```

Since you're not doing RL, the delegation policy has to come from prompting. What to
put in the sub-agent system prompt, derived from what RAO's reward was actually
shaping:

- **Delegate for breadth, not depth.** "Find every call site of X" delegates well;
  "carefully refactor this function" does not.
- **Specify the return shape in the goal.** The parent should say what it wants back
  and in what format. RAO's reward included a delegation bonus proportional to the
  *success rate* of children (λ · mean child success, λ = 0.4 in their runs),
  explicitly normalized so that spawning more children isn't itself rewarded. Encode
  the same pressure in the prompt: fewer, better-specified sub-tasks.
- **Never delegate what you can answer from context you already hold.**

Log every tree — depth, branching, per-node tokens, per-node success — from day one.
That log is your evaluation data, and it's also the dataset if you ever do 6.6.

### 6.6 Optional: actually training a recursive policy

Only if you want the research project. You'd need an open-weights model (the paper
used Qwen3-4B-Instruct-2507 and Qwen3-VL-30B-A3B-Instruct — small enough to be
tractable), an RL stack, and a verifiable task distribution. Terminal-Bench (Phase 7)
gives you exactly that: binary pass/fail per task is a clean root reward.

The RAO recipe, for reference:

- **Local node reward:** `R(X, τ_X) = s̃(X, τ_X) + λ · (1/|C(X)|) · Σ_{c ∈ C(X)} s̃(c, τ_c)`
  — own success plus a delegation bonus from the *mean* success of immediate
  children. Second term is zero for leaves. λ = 0 once the policy already delegates
  enough on its own.
- **Sub-agent success signal `s̃`:** exact verification where available; otherwise an
  LLM judge (they used GPT-5-mini); otherwise fall back to root-task success as a
  proxy. Credit assignment gets more faithful as `s̃` gets more local.
- **Advantage:** leave-one-out baseline over the G root rollouts, `b₋g = mean of
  other roots' rewards`, applied to *every* trajectory in the tree including
  children. Not lowest-variance, but it avoids needing a critic or per-subtask
  comparison groups.
- **Depth-level inverse-frequency weighting:** `w_d = α / N_d`, normalized to
  preserve total batch weight. Without it, deep levels vastly outnumber roots and
  dominate the gradient.

Realistically: do 6.1–6.5, ship it, and revisit this only if the logs show the
scaffold underperforming for reasons that look like *policy* failures rather than
*engineering* failures.

## Phase 7 — Benchmarking on Terminal-Bench

You cannot tell whether any of the above worked without a number. Terminal-Bench is
the right target: real terminal tasks in containers, pass/fail verified by tests,
which is exactly Kai's shape.

⚠️ Verify the CLI details below against current docs before building — the harness
was renamed from `tb` (Terminal-Bench 1.x) to `harbor` (Terminal-Bench 2.0) and
flags have moved.

### 7.1 Setup

```bash
uv tool install harbor          # requires Python 3.10+, and Docker running

# smoke test: runs oracle solutions on 5 tasks, validates your install
harbor run -d terminal-bench/terminal-bench-2 -a oracle --n-tasks 5
```

Get the oracle passing before you touch your own agent. Almost every "my agent
scores 0" report is a broken harness install.

### 7.2 The adapter

New package `kai/eval/terminal_bench.py`. Subclass `BaseAgent` and implement the
single required method:

```python
from pathlib import Path
from harbor.agents.base import BaseAgent, AgentResult
from harbor.terminal.tmux_session import TmuxSession

class KaiAgent(BaseAgent):
    @staticmethod
    def name() -> str:
        return "kai"

    def perform_task(
        self,
        task_description: str,
        session: TmuxSession,
        logging_dir: Path | None = None,
    ) -> AgentResult:
        ...
```

Run it:

```bash
harbor run -d terminal-bench/terminal-bench-2 \
  --agent-import-path kai.eval.terminal_bench:KaiAgent \
  -m anthropic/claude-sonnet-5 \
  -k 5
```

Two integration strategies — pick the second:

- **Drive tmux.** Type into the session as if you were a human. Faithful to how the
  harness thinks about agents, but you're parsing terminal output, which is misery.
- **Install and run headless.** `pip install kai` into the container, run
  `kai -p "<task_description>" --output-format json`, parse the NDJSON. This makes
  **Phase 5.1 a hard prerequisite** for Phase 7. Cleaner, faster, and the JSON stream
  gives you per-tool telemetry for free.

Wire `AgentResult` properly — return real input/output token counts (you have them
from Phase 1.2) and set a failure mode on error. The failure-mode field is what makes
a 40% score diagnosable instead of merely disappointing.

### 7.3 What to measure

Score alone is close to useless for driving development. Log per task:

- pass/fail, wall-clock, total tokens, **cost per solved task**
- turn count, tool-call histogram, peak context utilization
- compaction events, interrupts, permission denials
- once Phase 6 lands: tree depth, branching factor, per-node token spend,
  serial vs. parallel child time

Cost-per-solved-task is the metric that actually guides decisions. An agent that
solves 45% at $0.30/task beats one that solves 50% at $4.00/task for nearly every
real use.

### 7.4 Making it a development loop, not a scoreboard

- Curate a **fast subset** (~15 tasks, mixed difficulty) that runs in a few minutes.
  Run it on every meaningful change. The full suite is for milestones.
- Add a `task bench` and `task bench:quick` target to `Taskfile.yml`.
- Store results as JSON in `bench/results/<git-sha>.json`, committed. Add a
  regression check that fails if pass rate drops more than N points against the
  previous commit.
- Scale out with `--env daytona -n 32` when you need the full suite quickly.
- Keep a `bench/failures/` directory of transcripts from failed tasks. Reading five
  of those teaches you more about what to build next than the aggregate number will.

### 7.5 Baselines worth having

Run these once each so your own numbers mean something:

1. Kai v2 (today's code) — the floor.
2. Kai v3 after each phase — isolate what each one bought you.
3. Kai in JSON mode vs. code mode (6.2) at fixed model and budget.
4. Kai with recursion off vs. on (6.1) — the paper's central comparison, and the
   most interesting number you'll produce.
5. A published agent on the same model, as a sanity check that your harness isn't
   silently broken.

Comparison 4 is the one to care about. The paper's claim is that recursion lets a
small context beat a large one; if you can reproduce even a weak version of that
without training, Phase 6 justified itself.

## Suggested order of work

1. **1.1 + 1.2** — output budgets and token accounting. Everything downstream needs them.
2. **1.4 + 1.5** — cancellation and retries. Small, high relief.
3. **1.3** — compaction. Depends on 1.2.
4. **3.1** — provider abstraction. Do it before the code grows; retrofitting later is
   much worse. Groq's tool-calling is the weakest link in v2 and you'll want to
   swap models while working on everything else.
5. **2.1 + 2.2** — permissions and plan mode.
6. **3.3 `todo_write`** — one afternoon, disproportionate payoff.
7. **5.1 + 7.1 + 7.2** — headless mode and the Terminal-Bench adapter. Do this
   *before* Phase 6, not after. You need a baseline number to know whether recursion
   helped, and headless mode is a prerequisite for the adapter anyway.
8. **4.1 + 4.2** — project memory and slash commands.
9. **4.3** — persistence.
10. **6.2 + 6.3** — code mode and handles. Large context reduction on their own,
    and they're the prerequisite for recursion.
11. **6.4 (`DockerSandbox`)** — you need isolation before concurrent children.
12. **6.1 + 6.5** — the delegation primitive and its budgets. Measure against the
    Phase 7 baseline immediately.
13. Everything else, by taste.

Phases 6 and 7 are interlocked on purpose. Building recursion without a benchmark
means you'll have an elaborate architecture and no idea whether it helps — which is
the specific failure mode the RAO authors are pointing at when they note that most
recursive systems are untrained scaffolds.

## Design principles to hold onto

- **Stay hackable.** The README's pitch is "minimal, hackable." Each phase should
  add a module, not thread conditionals through existing ones. If `message_loop.py`
  passes ~400 lines, something belongs elsewhere.
- **The model is a user of your API.** Tool descriptions, error messages, and
  truncation markers are prompt engineering. A tool error that says what to do next
  is worth more than one that's merely accurate.
- **Never silently drop state.** Compaction, truncation, and interrupts must all
  leave a visible marker — for the user in the transcript, and for the model in
  the context.
- **Cheap model for cheap work.** Compaction, session titles, and search subagents
  should never run on the main model.
- **Context is the budget.** Every design question in Phases 1, 6.2, and 6.3 reduces
  to: does this token need to be in the model's window, or can it live in a variable,
  a file, or a child's context instead? Prefer a handle over text, a child over a
  summary, and a summary over the raw thing.
- **Measure before you architect.** Phase 6 is the largest change in this document
  and the one most likely to be a wash. Do not build it without the Phase 7 number
  in hand.
